# 向量化阶段基准 / Embedding Stage Benchmark（增量 3）

> 目的：为「向量化并发与缓存」提供可复算验收数据。
> 本文只回答一个问题——**向量化阶段的时间花在哪，缓存与并发各能拿回多少，代价是什么**。
> 与 `V5_PARSE_CACHE_BENCHMARK.md`（增量 2）的关系：那份覆盖「解析」这段 CPU 密集的
> 本地工作，本文覆盖「向量化」这段远程 HTTP 工作，两者的缓存机制同源、收益来源不同。

---

## 1. 结论摘要

| 项 | 结果 |
|---|---|
| **热缓存** | 426.64 s → **1.65 s（258×）**，请求数 592 → **0**（9,459 块全部命中） |
| **并发（本地 ollama）** | 426.64 s → 414.82 s（**1.03×**）——服务端推理串行，HTTP 并发只是排队 |
| 并发（可控端点，服务端可并行） | 43.16 s → 6.85 s（**6.30×**） |
| 连接复用 | 逐批自建连接 → 复用长连接：受控端点 L=0 档 **1.48×**（592 条连接 → 1 条） |
| 写缓存代价（冷跑） | 414.82 s → 424.93 s（**+2%**），落盘 256 个分片 |
| 产物等价 | 四个场景（冷跑 / 并发 / 写缓存 / 热跑）**repr 级同一指纹 `2acf817a0d96ba5c`**（见 §6） |

一句话：**缓存在这里是数量级的，并发不是**——并发是否有收益完全取决于服务端能否并行处理
请求；本机单实例 ollama 不能，所以 8 路并发只换来 1.03×。

## 2. 方法与测量环境

- **切片**：真实 Java 项目 `ucap-cloud-back`，3,797 个文件 / 3,552 个可解析文件 /
  **9,459 块** / **592 批**（批 16）/ 13.2 MiB 文本。
- **模型**：`embeddinggemma-2:latest`（= 740m，1.26 GB），ollama 0.40.2，**MLX runner**，
  **768 维**，`size_vram` 1.27 GB —— 整个模型驻留在统一内存里，推理在 GPU 侧。
- **单批延迟**：批 16 短文本（约 10 token/条）稳态 **150–200 ms**；真实块平均约 1,460 字符
  （约 400 token/条）时约 **720 ms**。**批延迟随 token 量近似线性**，这是后面所有绝对秒数的量纲来源。
- **四个场景全部走生产代码路径**，不是另写的仿真：
  - **A 旧路径**：按 16 切批调用 `Embedder.embed()` —— 改动前 `jobs.py` 的索引行为，
    且 `embed()` 每次自建 `httpx.Client`（每批一条新连接），串行；
  - **C 新路径**：`embed_many(concurrency=8)` + 注入长生命周期 client；
  - **E 新路径 + 写缓存**：在 C 上接向量缓存（冷跑：请求 + 分片落盘）；
  - **D 新路径 + 读缓存**：新一代际、新实例读盘（热跑：零请求）。
- 另有**可控延迟的本地 mock 端点**（延迟是参数，服务端可并行）用来把「结构」与「模型延迟」
  分开测量，见 §3。

## 3. 结构基线：mock 端点（服务端可并行）

同样的 9,459 块 / 592 批，把「一次请求的往返延迟」当参数（L），服务端可并行：

| 场景 | L = 0 ms | L = 50 ms |
|---|---|---|
| A 旧路径（逐批自建连接） | 5.89 s / **592 条连接** | 43.16 s |
| B 串行 + 复用连接 | 3.97 s / **1 条连接**（1.48×） | 40.26 s（1.07×） |
| C 并发 8 + 复用连接 | 3.97 s（1.49×，峰值 3 路） | **6.85 s（6.30×**，峰值 8 路） |
| 热缓存 | 0 s / 0 请求 | 0 s / 0 请求 |

三点读法：

1. **连接复用在「本地开销主导」时才明显**（L=0 档 1.48×）；一旦往返延迟占主导（L=50 ms）
   就只剩 1.07×，因为握手成本被延迟淹没了。这解释了为什么它必须和缓存/并发一起做才有意义。
2. **并发的上限是 6.3×，不是 8×**——差值来自 HTTP + JSON 序列化卡在 GIL 上。
3. L=0 档峰值只有 3 路：请求太快，线程来不及重叠，算是「并发无用的下界」。

## 4. 决定性发现：瓶颈在「新建文件」这个动作，与文件多大无关

向量缓存最初按解析缓存的样子写成「一条一个文件」。实测下来这在本机是灾难：

| 单个文件大小 | 每文件写入耗时 | 折算吞吐 |
|---|---|---|
| 1 KiB | 14.89 ms | 0.07 MB/s |
| 8 KiB | 13.36 ms | 0.58 MB/s |
| 15 KiB | 14.18 ms | 1.01 MB/s |
| 150 KiB | 14.45 ms | 9.90 MB/s |
| 1.5 MiB | 14.85 ms | 96.32 MB/s |

**耗时与体积几乎无关，恒定约 14.5 ms/文件。** 分层定位：

| 层次 | 每次新建文件 |
|---|---|
| shell 重定向（`> file`） | **83 ms** |
| Python 裸 `os.open`/`write`/`close` | 4.2 ms |
| 同一文件内连续写 100 次 | **0.14 ms/次** |
| `builtins.open` | 已被替换为 `_brokered_builtin_open`（宿主 broker 包装） |

结论：**代价在「创建新文件」这个动作本身**。9,459 条向量一条一个文件，单轮写缓存就要
约 250 s（首次验收里 D 场景实测 256.49 s 即由此而来）；改成 **2 位哈希前缀分片、256 个
分片文件、整片批量重写**后降到约 1 s。这也是 `EmbeddingCache.put` 只改内存、
由 `flush()` 合并落盘的原因。

> 该 14.5 ms/文件的开销是本机（macOS + 宿主 broker 包装 `open`）的测量值，不同环境数值会变，
> 但「减少文件数」在任何环境都是正向优化，因此分片是通用设计而非本机特调。

## 5. 真实模型验收（EmbeddingGemma-2 740m @ 本机 ollama）

9,459 块 / 592 批 / 768 维，单进程内依次执行：

| 场景 | 耗时 | 请求数 | 连接数 | 相对 A | 向量指纹 |
|---|---|---|---|---|---|
| A 旧路径（逐批自建连接，串行） | **426.64 s** | 592 | 592 | 1.00× | `2acf817a0d96ba5c` |
| C 新路径（并发 8 + 复用连接） | 414.82 s | 592 | 8 | 1.03× | `2acf817a0d96ba5c` |
| E 新路径（并发 8 + 写缓存） | 424.93 s | 592 | 8 | 1.02× | `2acf817a0d96ba5c` |
| **D 新路径（新一代际 + 热缓存）** | **1.65 s** | **0** | 8 | **258×** | `2acf817a0d96ba5c` |

- **缓存是数量级的**：热跑零请求、零模型调用，258× 全部来自「不发请求」。
- **写缓存的代价可以忽略**：E 比 C 只慢 2%（256 次分片写 ≈ 4 s，摊在 425 s 里）。
- **并发在本地模型上几乎无效**：8 路只拿到 1.03×。原因不是实现，而是**服务端吞吐固定**——
  模型跑在 MLX runner 上、常驻统一内存，ollama 一次只推进一个推理，HTTP 并发只是把请求排进队列。
  收益的开关在服务端（`OLLAMA_NUM_PARALLEL` 及显存），不在客户端。
- **A 之所以是 427 s**：592 批 × 约 0.72 s/批（真实块约 1,460 字符），加上每批新建连接的握手成本。
- **四场景指纹同为 `2acf817a0d96ba5c`**：缓存与并发只改变速度，不改变产物——这正是 §6 那个缺陷
  修复后的端到端证据。

## 6. 顺带修掉一个「缓存改变产物」的真实缺陷

首次验收时四个场景的向量指纹不一致：A/C/E 都是 `4d8f79077d8158c4`，D 是 `2acf817a0d96ba5c`。
排查过程与结论：

- **缓存读写本身是正确的**：用盘上的缓存复算指纹，恰好等于 D 的指纹；受控实验也显示
  `put` → `get` 往返一致。
- **差异在「请求返回值」与「写入缓存的值」之间**，且**逐值比较 `==` 全部相等**
  （`v_e == v_c` 为 `True`），只有 `repr` 级指纹不同 —— 差异扫描因为用 `!=` 判定而完全漏掉它。
- **根因**：模型把**恰好为整数的分量序列化成 JSON 整数**（`0` 而非 `0.0`），`json.loads`
  给出 `int`；而缓存 `put` 会把元素归一化成 `float`。于是**未命中产出 `int`、命中产出 `float`**，
  `0 == 0.0` 为真却 `repr(0) != repr(0.0)`，缓存因此悄悄改变了产物。
- **修复**：`Embedder._request` 在校验后统一 `float(...)` 归一化，两条路径都只产出 `float`。
  修复后同一受控实验（1,000 块）两条路径 **repr 级一致**（指纹均为 `1ac5159eaa2469f5`）。
- **教训**：等价性门槛必须细到 `repr`。`==` 判不出 `int`/`float`、`-0.0`/`0.0` 这类差异。
  回归用例：`test_cache_hit_matches_miss_down_to_repr`、`test_integer_components_are_normalized_to_float`。
- **端到端确认**（修复后以真实模型完整重跑）：A/C/E/D 四场景指纹**全部等于 `2acf817a0d96ba5c`**，
  热代际 `hits=9459 / misses=0`，脚本自检输出「产物指纹全部一致，热缓存零未命中」（见 §5）。

## 7. 未验证与已知边界

1. **并发收益不可移植**。本机 1.07× 是「服务端串行」的结果；换成交互式云端嵌入 API（服务端可并行）
   时应参考 §3 的 6.30×。部署前应先确认服务端并发度，否则并发只是增加在途请求数。
2. **分片让淘汰粒度变粗**。`enforce_budget` 现在按分片文件淘汰，一个分片最多约 1/256 的块会一起失效
   （约 37 块 / 370 KiB），不再精确到单条向量。
3. **模型语义质量未评测**。本文只测吞吐与产物一致性，不评价 `embeddinggemma-2` 的检索质量。
4. **真实块的批延迟（约 720 ms）只在本机这一档测得**，换机器/换量化会变；所有倍数结论不依赖它。
5. **并发与取消的边界**：`should_stop` 在每批开始前求值，但 Python 3.11 的 `Executor.map`
   会一次性提交全部批次，因此取消是「尽快停下」而非「精确停下」——已在提交但未开始的批次仍会跑完。

## 8. 复算方式

```bash
# 结构基线（可控端点，服务端可并行；脚本内 mock 端点）
.venv/bin/python tmp/embed_accept.py

# 真实模型验收（需要本机 ollama + embeddinggemma-2:latest）
.venv/bin/python tmp/embed_accept_real.py

# 回归用例
.venv/bin/python -m pytest tests/service/test_embedding_cache.py tests/service/test_embedding_batch.py -q
```

> **沙箱内跑测试的两个坑**（都会表现为「全部 ERROR、0 断言失败」，不是代码回归）：
> 1. `tmp_path` 默认落在 `/private/var/folders/.../T/`，会被宿主 broker 拒绝 `mkdir`；
>    需要用工作区内的 basetemp：`--basetemp=<repo>/tmp/pytest-base`。
> 2. `tests/conftest.py` 的 autouse fixture `isolated_dsh_home` 每个用例都会
>    `tmp_path_factory.mktemp(...)`，其清理删除会消耗**每回合 50 次**的批量删除额度；
>    额度耗尽后所有用例在 setup 阶段就 `SystemExit: 1`。全量跑需要提权（绕过沙箱）才会全绿：
>    `234 passed, 39 skipped`（39 条跳过均为「需要隔离 PostgreSQL 验证数据库」）。
