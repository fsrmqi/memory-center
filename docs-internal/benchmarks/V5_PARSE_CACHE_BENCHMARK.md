# 解析缓存基准 / Parse Cache Benchmark（增量 2）

> 目的：为「增量解析与解析缓存」提供可复算验收数据。
> 本文只回答一个问题——**文件内容没变时，一次索引能不能跳过它的解析，代价是多少**。
> 与 `V5_SERVICE_INDEX_STAGE_BASELINE.md`（增量 1 基线）的关系：那份测「时间花在哪」，
> 本文测「缓存的收益与代价」，并在 §2 复核该文档的部分数值。

---

## 1. 结论摘要

| 项 | 结果 |
|---|---|
| 产物等价 | 冷跑产物与热跑产物**深度相等**（通用代码图 + Java 专用事实，各 3 轮） |
| 通用结构解析 | 池化无缓存 1.64 s → 热缓存 0.86 s（**1.9×**） |
| Java 专用解析 | 池化无缓存 5.02 s → 热缓存 0.45 s（**11×**） |
| 两段解析合计 | 6.54 s → 1.31 s（**5.0×**） |
| 冷跑额外成本（写缓存） | 与无缓存持平（−2% ~ +5%，在噪声内） |
| 缓存体积 | 61.3 MiB（通用 26.5 + Java 34.8）/ 12.7 MiB 可解析源码 = **4.8×** |

一句话：**冷跑几乎不额外付费，热跑省掉绝大部分解析与全部重复读取**（重复读取的消除见 §7、§9）。

## 2. 复核：与增量 1 基线文档的差异

同一台机器、同一份切片，本轮的串行/池化数字与增量 1 文档**不一致**，先说明清楚：

| 阶段 | 增量 1 文档 | 本轮受控测量（串行） | 说明 |
|---|---|---|---|
| chunking（读+切块+哈希） | 10.64 s | 0.26 s | 相差 40× |
| build_code_graph | 17.17 s | 6.61 ~ 7.75 s | 相差约 2.3× |
| Java 专用解析 | 42.20 s | 30.84 ~ 31.53 s | 相差约 1.35× |

差异最大的是纯 IO 阶段（chunking），说明增量 1 那次运行处于**页缓存冷 + 机器负载高**
的状态（该次运行与多个后台任务同时进行）。因此：

- 本文的所有结论只用**同一次进程内**的相互比较（串行 / 池化 / 冷 / 热），
  不跨运行引用绝对值；
- 增量 1 文档的**比值**结论（线程不可用、进程池 2.5×、关系解析仅占 4%）不受影响，
  因为它同样来自单次运行内的比较；
- 增量 1 文档的**绝对秒数**（70.0 s 等）应视为高负载条件下的上界，不要用作对比基准。

## 4. 主表（单次受控运行）

同一次进程内的四个对照，文件表完全相同：

| 阶段 | 串行·无缓存 | 池化·无缓存 | 池化·冷缓存 | 池化·热缓存 |
|---|---|---|---|---|
| 通用结构解析（`build_code_graph`） | 6.61 s | 1.53 s | 1.61 s | **0.81 s** |
| Java 专用解析（`_parse_java_file`） | 31.53 s | 5.06 s | 4.83 s | **0.41 s** |
| **解析两段合计** | 38.14 s | 6.59 s | 6.44 s | **1.22 s** |
| 等价性 | — | 与串行相等 | 与串行相等 | 与冷跑相等 |

产出：15,400 个符号、4,243 条已解析调用边、3,552 份 Java 符号、1,311 个 API 端点。

「冷缓存」= 缓存目录为空的一次运行（需解析并写缓存）。它与「池化·无缓存」的差
（1.61 vs 1.53、4.83 vs 5.06）在运行间波动范围内，即**写缓存的开销可忽略**：
写盘发生在 worker 内部、与解析重叠，且 3,552 个条目分片到 256 个子目录。

## 5. 重复测量与方差

单次运行的噪声不可忽略（同机重复运行波动 ±20%），故对关键阶段取多轮结果：

| 阶段 | 池化·无缓存 | 池化·冷缓存 | 池化·热缓存 |
|---|---|---|---|
| 通用结构解析 | 1.53 / 1.64 / 1.72 → 中位 **1.64** | 1.61 / 1.71 / 1.72 → **1.71** | 0.81 / 1.27 / 专项复测 0.86 → **0.86** |
| Java 专用解析 | 4.29 / 4.60 / 5.06 / 5.02 / 5.70 → 中位 **5.02** | 4.49 / 4.83 / 4.93 → **4.83** | 0.40 / 0.41 / 0.45 / 0.47 / 0.51 → **0.45** |

按中位数计算的加速比：

| 阶段 | 池化·冷缓存 → 池化·热缓存 |
|---|---|
| 通用结构解析 | 1.71 → 0.86 = **1.99×** |
| Java 专用解析 | 4.83 → 0.45 = **10.7×** |
| 两段合计 | 6.54 → 1.31 = **5.0×** |

### 命中时刷新时间戳的代价（专项测量）

淘汰按「最近使用」而非「最近解析」排序，因此命中时会 `utime` 刷新时间戳。代价单独量过：

| 项 | 耗时 |
|---|---|
| `utime` × 3,552（单进程串行） | 0.114 s |
| 热跑 touch=on（3 轮） | 1.047 / 0.849 / 0.838 s |
| 热跑 touch=off（3 轮） | 0.861 / 0.846 / 0.813 s |
| 热跑 touch=on 复测（2 轮） | 0.879 / 0.860 s |

刷新摊到 8 个 worker 后约 14 ms，与噪声同级；可忽略。

## 6. 一遍索引的推算（切片）

扫描与切块不受本次改造影响，且**尚未与解析合并**（见 §8），故单列：

| 项 | 耗时 |
|---|---|
| scan（目录枚举） | 0.21 ~ 0.42 s |
| chunking（读取 + 切块 + 哈希 → 9,459 块） | 0.26 ~ 0.50 s |

把 §5 的中位数与固定开销相加，得到切片上一次服务侧索引的两段解析部分：

| 场景 | 解析两段 | 加上扫描+切块 |
|---|---|---|
| 冷跑（首次索引） | 6.54 s | ≈ 7.0 s |
| 热跑（没有任何文件改动） | 1.31 s | ≈ 1.8 s |
| 相对冷跑 | **5.0×** | ≈ 3.9× |

**说明**：scan/chunking 在 §4 的测量序列末尾取得，此时页缓存已热，应视为**下界**。
真实一次索引还含知识库、向量化、逐服务写入与发布阶段，本文不含这些。

## 7. 缓存体积与预算

| 命名空间 | 条目 | 体积 | 载荷 / 源码 |
|---|---|---|---|
| `structural`（通用结构解析） | 3,552 | 26.5 MiB | 2.1× |
| `java`（Java 专用事实） | 3,552 | 34.8 MiB | 2.7× |
| 合计 | 7,104 | **61.3 MiB** | **4.8×** |

按 4.8× 线性外推，全工作区（175.0 MiB 源码）的缓存约 **840 MiB**。b12 的默认预算是
固定的 512 MiB，这类工作区**必然触发淘汰**；b13 起默认预算按工作区规模自适应：

```
默认预算 = clamp(可解析源码字节 × 6, 512 MiB, 4 GiB)      # 显式 env 仍然优先
```

175 MiB 源码 → 1050 MiB，足以容纳约 840 MiB 载荷，一次建满即可长期命中；小工作区
仍保底 512 MiB，不受影响。仍可通过 `MEMORY_CENTER_PARSE_CACHE_MB` 显式覆盖
（`0` 关闭、正数固定、非法值退回自适应）。若预算仍小于实际载荷，超出的部分按
「最近使用」淘汰，被淘汰的文件下次重新解析，**产物不受影响**，只是收益打折。

淘汰顺序按「最近使用」排序：一轮索引结束后，仍在用的条目时间都是新的，
源码已改过或已删除的旧内容条目时间停在最后一次被读到的时刻，**先于在用条目被淘汰**。

## 8. 增量 2 验收

| 项 | 阈值 | 实测 |
|---|---|---|
| 产物等价 | 冷跑产物 == 热跑产物（含 coverage / edges / units，深度相等） | ✅ 结构 3 轮、Java 3 轮 |
| 与串行一致 | 池化 + 缓存产物 == 串行无缓存产物 | ✅ |
| 解析加速 | 两段合计 ≥ 3.0×（热 vs 冷） | ✅ 5.0× |
| 冷跑代价 | ≤ +15% | ✅ −2% ~ +5%（噪声内） |
| 精确失效 | 只有内容变化的文件未命中 | ✅ N−1 命中 |
| 解析器不可用 | 不落缓存（避免把「缺绑定」固化成结果） | ✅ 用例覆盖 |
| 缓存故障 | 损坏 / 只读 / 不可序列化 → 只退化为未命中，不中止索引 | ✅ 用例覆盖 |
| 键隔离 | 命名空间 / 语言 / 内容 / 项目 / 路径任一不同即不同键 | ✅ 用例覆盖 |
| 预算淘汰 | 超预算按最近使用淘汰，不跟随符号链接 | ✅ 用例覆盖 |
| 既有合同 | 取消、原子发布、MCP tool schema、`StructuralParseResult` 形状不变 | ✅ 未触碰 |

用例：`tests/service/test_parse_cache.py`（23 项）。

## 9. 已修复的边界与未验证项

1. **~~未合并三遍读取~~（b13 已消除）。** b12 时缓存的键仍要求「读文件 + 算 sha256」，
   同一份源码在 `chunking` / `build_code_graph` / Java 解析三处各自读一遍、各自算一次
   哈希。b13 把扫描/切块阶段顺带算出的内容 sha256 传给两条解析路径（`build_code_graph`
   的 `digests`、`reindex_workspace` 的 `source_digests`），解析先按键查缓存，**命中即不读源码**。
   逐文件读取次数：

   | 场景 | 修复前 | 修复后 |
   |---|---|---|
   | 热跑（缓存命中） | 3 次读 + 3 次哈希 | **1 次读 + 1 次哈希**（解析阶段零读取） |
   | 冷跑（缓存未命中） | 3 次读 + 3 次哈希 | 3 次读 + **1 次哈希** |

   热跑不再重复读取，可用「删除源文件后仍命中」直接验证（
   `tests/service/test_parse_cache.py::test_parse_file_unit_hit_with_supplied_digest_does_not_read_source`）。
   冷跑为何仍读：结构性解析与 Java 专用解析消费不同产物，两者都需要源码文本，缓存能省掉
   其中一次「解析」，省不掉它们各自的「读取」。此外 b13 起 Java 延迟 Feign 解析不再把源码
   文本内嵌进 `pending_feign`，改为在 Feign 阶段按绝对路径读取（只有 Feign 接口自身需要）。
   未提供 digest 的调用方（如直接调用 `build_code_graph` 的测试）退回旧行为，产物逐值不变。
2. **未测多项目并发下的缓存争用。** 不同工作区写各自的缓存目录，理论上无冲突；
   同一工作区由代际锁串行，故不会并发写同一目录。但未实测。
3. **未测向量化阶段。** 本次未配置嵌入模型。
4. **全工作区为线性外推**，未整仓实测。
5. **缓存目录目前没有独立的清理入口。** 它随工作区目录保留，唯一的自动收敛机制是
   预算淘汰；仓库现有的 `prune` 只处理 `generations`，不处理 `parse-cache`。
6. **`CACHE_SCHEMA` 是人工契约。** 任何会改变解析输出的实现改动都必须递增它，
   否则旧载荷会被当新结果复用。当前无自动化守卫。

## 10. English Summary

Increment 2 adds a content-addressed file-level parse cache keyed by
`(schema, namespace, file identity, language, content sha256)`. On the same real module
(3,552 parseable Java files, 12.7 MiB) measured within a single process, a warm cache takes
the generic structural parse from 1.64 s to 0.86 s (1.9×) and the Java-specific parse from
5.02 s to 0.45 s (11×) — **5.0× across both parse stages** — while a cold run pays no
measurable extra cost for writing the cache. Cold and warm outputs are deep-equal to each
other and to the uncached serial reference in every measured run. The cache occupies 4.8×
the parseable source size (61.3 MiB here). The b13 follow-up removes the duplicate reads and
scales the default budget with the workspace (`max(512 MiB, parseable source × 6)`, capped at
4 GiB, so a 175 MiB workspace gets about 1050 MiB instead of a fixed 512 MiB): the sha256
computed during scanning/chunking is handed to both parse paths, which probe the cache by that
key first, so a warm run reads each file once and performs no read at parse time.
