# DSH Memory Center 工作台产品化路线 / Productization Roadmap

> 文档类型：产品与实施路线（current）  
> 首个落地场景：单一 UCAP workspace。  
> 本路线不扩展第二个 workspace 或跨 Agent 采集；这些方向仅在真实使用证明需要后再进入排期。

## 1. 产品定义 / Product Definition

**一句话定位**：DSH 本地工作台是面向 AI 工作的项目与方法中枢，让使用者完成“选择思考方法、理解当前任务、判断影响、完成交付、沉淀长期知识”。

它不是通用聊天历史、通用项目管理工具，也不是第二个代码索引器。

| 用户问题 | 工作台必须给出的答案 |
|---|---|
| 刚打开项目，不知道从哪里继续 | 当前任务是什么？下一步是什么？缺什么？ |
| 改动前不知道风险 | 会影响什么？哪些是事实、哪些只是推断？ |
| 做完一次 DSH 工作后信息会丢 | 这次交付、验证、来源和任务归属是什么？ |
| 不知道哪些经验应长期保留 | 哪些是项目内记忆，哪些值得确认晋升到 Wiki？ |
| 不知道该怎样问 AI 或采用哪种思考方式 | 当前问题适合什么方法？还该补哪些信息？ |

## 2. 产品边界 / Product Boundaries

```text
DSH：交互入口、受限展示、执行与交付信号
Memory Center：当前项目事实、任务、影响、证据、Case、回执
Personal Wiki：人工确认后的长期知识正文
```

- DSH 不保存第二套项目事实，不自动写长期 Wiki。
- Memory Center 不复制完整 Wiki 正文或完整聊天 transcript。
- Personal Wiki 不替代当前源码、图谱或任务证据。
- 当前工程证据与 Wiki 冲突时，优先当前工程证据。

## 3. 核心产品主线 / Core Journey

```text
进入工作台
→ 需要时进入方法工坊，选择思考方法
→ 从当前对话提取结构化输入草稿
→ 确认后发送方法 Prompt 到当前 DSH 会话
→ 确认当前任务与下一步
→ 影响分析
→ DSH 实施与验证
→ 自动交付摘要
→ 任务级回执与交接
→ Case / Wiki 晋升预览
→ 用户确认后沉淀长期知识
```

任何页面、指标或图谱都必须服务这条主线；无法帮助用户做下一步决策的内容进入二级视图或移除。

## 4. 信息架构 / Information Architecture

| 页面 | 主问题 | 首屏内容 | 二级内容 |
|---|---|---|---|
| 概览 | 我现在该做什么？ | 焦点任务、下一步、风险、最近进展 | 任务队列、健康状态 |
| 任务 | 如何继续并完成交付？ | 当前阶段、交付摘要、验证、未解决项 | 交接、Case、Wiki 晋升 |
| 分析 | 会影响什么？ | 结论、风险分层、下一步建议 | 直接证据关系、结构化图谱 |
| 知识 | 有哪些可复用知识？ | 项目记忆、相关 Wiki、关联原因 | 交付记录、待审批候选 |
| 运行 | 本次 DSH 为什么慢或失败？ | 当前会话状态、耗时、错误 | 模型/工具明细、Token |
| 方法工坊 | 我该怎样思考或提问？ | 方法选择、问题输入、Prompt 预览 | 对话提取、方法说明、发送状态 |

页面统一规则：首屏只给“结论 + 下一步”；原始事件、长摘要、完整图谱与内部字段一律按需展开。

## 5. 实施路线 / Delivery Phases

### Phase A：体验基线与设计系统（1 个迭代）

目标：停止逐页面补丁，统一信息层级与组件语言。

实施项：

1. 固定“Memory Center 工作台 + 方法工坊”双入口职责和首屏信息预算。
2. 定义统一组件：任务卡、状态 badge、结论 banner、下一步卡、证据关系行、空态、错误态、加载态。
3. 制定视觉 token：背景、面板、正文、弱文本、成功/警告/阻塞/推断色、间距、圆角、阴影。
4. 删除“全是 0 的卡片”“内部 L0 名称”“原始 Markdown 摘要”“无方向蜘蛛网”。
5. 建立 UI 截图回归基线：概览、任务、分析、知识、运行各一张真实数据截图。

验收：用户在不阅读说明的情况下能在 10 秒内识别焦点任务、下一步和阻塞；页面不出现原始 Markdown、窄栏竖排按钮或重叠图标签。

### Phase B：方法工坊与任务成为第一等对象（1–2 个迭代）

目标：把“任务”页从信息列表变成可完成的交付面板。

实施项：

1. 方法工坊读取 Obsidian Prompt Catalog 的场景、用途、标签和内容哈希；不复制整库正文到 Memory Center。
2. 用户选择方法，填写问题、事实、约束和选项，先预览最终 Prompt 后才发送到当前 DSH session。
3. “从当前对话提取”仅本地提取问题、事实、约束、选项和未决项；不读取工具结果、代码块或密钥样式文本，不持久化。
4. DSH session 创建时绑定当前 focus task；交付摘要、回执、Case 与 Wiki 候选都携带 `task_id`。
5. 任务页显示阶段：进行中、待验证、已完成、被阻塞。
6. 用一条任务时间线展示：开始、分析、交付摘要、验证、交接、晋升动作。
7. 将“下一步 / 未解决项 / 验证缺口”合并为一组可行动事项，而不是三个孤立面板。
8. 任务关闭时提供完整交接包与恢复入口。

验收：用户能在 10 秒内理解方法适用场景与预期产出；一次真实 DSH 交付只出现在正确任务中；新会话只看任务页即可知道该继续、验证、交接还是请求决策。

### Phase C：分析与验证决策（1–2 个迭代）

目标：让影响页真正支持改动决策，而不是展示关系图。

实施项：

1. 默认显示“无影响 / 需关注 / 需验证 / 被阻断”结论。
2. 分层展示 confirmed、probable、possible、unknown；零项不占主要空间。
3. 证据关系默认列表化，图谱作为切换视图；结构只展示有限上游、目标、下游。
4. 在结论下直接提供验证建议、停止条件与进入任务的动作。
5. 为每个分析结果显示索引新鲜度与证据等级。

验收：用户能区分“静态关系”“需要修改的影响”“还需验证的风险”；不会因为图谱存在而误认为结论已确认。

### Phase D：知识产品化（1–2 个迭代）

目标：让项目记忆和长期 Wiki 在同一界面协同，但不混淆事实源。

实施项：

1. 知识页分为：项目记忆、已关联 Wiki、按需 Wiki 命中、待晋升知识。
2. 每条 Wiki 显示关联原因、scope、来源引用、哈希状态和“当前工程优先”的边界。
3. 任务标题、标签、影响目标共同形成 Wiki brief 查询，不仅使用任务标题。
4. 交付摘要 → Wiki 预览 → 显式确认 → 资产回写形成可见时间线。
5. Wiki 无命中时显示具体原因：未绑定、scope 不匹配、未索引或无直接知识，而非模糊空态。

验收：用户能知道某条 Wiki 为什么出现、何时过期、是否可晋升；确认前不发生任何 Wiki 正文写入。

### Phase E：性能、可靠性与发布（持续）

目标：让工作台可以日常打开，而不是功能演示。

性能预算：

| 路径 | 目标 |
|---|---:|
| 概览读模型 | P95 < 500ms |
| 本地 bridge 缓存命中 | < 100ms |
| 标签首次切换 | 明确加载态，避免阻塞其他页面 |
| 影响结论 | 先返回结论，证据关系可延迟加载 |
| Wiki brief | 按需调用、短 TTL 缓存、无命中可解释 |

实施项：

1. 每个 bridge 响应记录耗时、缓存命中、数据 generation 与降级原因。
2. 重型读模型只在对应标签激活时发起，取消离开页面后的无效请求。
3. bridge 按 workspace 按需启动、空闲回收、失败退避。
4. 建立真实 UCAP 性能基线和截图回归；发布前比较 P50/P95、错误率与首屏可用时间。
5. 所有失败必须显示“哪个数据源不可用、当前仍可做什么”。

验收：用户连续切换页面不出现卡顿或空白；任一 Wiki/bridge/索引失败不影响 DSH 对话与其余项目读取。

## 6. 数据合同 / Data Contracts

| 对象 | 必需字段 |
|---|---|
| DSH delivery summary | `source_session_id`、`turn`、`step`、`task_id`、摘要、capture boundary |
| Prompt method | `method_id`、Obsidian 相对路径、场景、用途、模式、内容哈希 |
| Conversation extraction draft | 问题、事实、约束、选项、未决项、仅内存范围 |
| Task delivery record | `task_id`、`session_id`、验证状态、回执引用、当前阶段 |
| Wiki asset | `pawiki:` 来源、`knowledge_id`、内容哈希、scope、关联原因 |
| Impact result | target、风险分层、证据等级、索引新鲜度、下一步 |
| Bridge response | workspace、耗时、缓存状态、降级原因（不含正文） |

新增字段必须 additive；不把 prompt、完整消息、工具参数/结果、Wiki 正文或私有源码放入工作台热路径。

## 7. 不进入当前路线的方向 / Deferred Directions

- 第二个真实 workspace 的切换验收；
- Codex、Claude 等外部 Agent 执行采集；
- 自动 Wiki 正文晋升；
- 全量 Wiki 导入；
- 跨 workspace Group 自动分析；
- 通用项目管理、协同看板或云端服务。

这些只有在当前 UCAP 单 workspace 的真实使用出现明确需求和证据后才立项。

## 8. 版本与验收节奏 / Release Cadence

每个阶段使用同一节奏：

1. 先用 UCAP 的一个真实任务定义验收截图与数据预期；
2. 实现最小读模型/动作；
3. 跑单元、入口、DSH Web smoke 与真实性能测量；
4. 用户在 DSH 完成一次真实任务；
5. 只根据该反馈修正下一阶段，不提前叠加未来能力。
