# Memory Center 5.0 改造流程方案

> 2026-10-09 当前实施更新：5.0.0b1 已接入多项目授权 MCP、后台索引、知识库/Wiki/记忆管理与 PG/向量后端，已完成本地测试版验收；正式发行仍需真实模型语义与规模评测。用户已授权连续实施。本轮证据见 [实施回执](implementation-receipts/V5_PLATFORM.md)，当前入口与合同见 [5.0 平台指南](V5_PLATFORM_GUIDE.md)。下方较早的 S1/S2 等待确认记录仅保留决策演进背景。


> 类型：决策与实施流程（decision）。日期：2026-10-09。
> 目标发行版：5.0.0；当前实现基线：4.6.30。当前开发分支：`codex/service-platform`。
> 状态：S0 已实施，包版本 5.0.0a1；尚未发布正式 5.0。S1 已实施（5.0.0a2），S2 等待用户确认后开始。实施证据见 [S0 回执](implementation-receipts/V5_S0_SERVICE.md) 与 [S1 回执](implementation-receipts/V5_S1_CATALOG.md)。
> 2026-10-09 决策修订：5.0 全新安装、重新登记项目并从源码重建；不导入 4.x workspace/registry/索引/记忆，不保留旧 CLI/MCP/HTTP/DSH 兼容层。历史数据由用户自行清理，本方案不执行删除。
> 本文件细化 [服务化技术方案](SERVICE_PLATFORM_TECHNICAL_PLAN.md) 的 S0–S5；[主计划](NEXT_PHASE_MASTER_PLAN.md) 仍是唯一开发优先级入口。

## 1. 版本目标与交付边界

5.0 将 Memory Center 从“按 workspace 启动的项目记忆工具”演进为“一次安装、常驻服务、多项目接入、MCP 能力共享、独立管理页面”的上下文与记忆服务。

5.0.0 必须交付：

- 本机单用户安装、启动、就绪检查、正常关闭和重新启动。
- 管理页面添加/预览/管理多个项目；项目使用稳定 ID，名称和路径可变。
- 一个统一 MCP 服务入口，按调用主体与请求范围隔离工程事实、任务和记忆。
- 代码索引、检索、调用链、影响分析和现有任务记忆继续由当前引擎提供。
- 后台索引进度、取消、重试、资源上限与失败恢复可观察。
- 全新服务数据目录与 5.0 接入配置，项目重新登记后从源码建立索引；不提供 4.x 数据迁移、旧接口兼容或跨版本降级。

文档知识库、Wiki、个人长期记忆和团队远程部署为后续 5.x 能力。5.0.0 必须预留来源、主体、空间和能力注册边界，但不将所有后续功能同时作为首版发布条件。

重建边界：代码索引从源码重新生成；历史 session、任务、案例与个人记忆不会由索引重建恢复，5.0 从空记忆状态开始积累。

每个切片按“证据核对 → 修改前影响分析 → 5.0 合同/测试 → 最小实现 → 真实流程验证 → 实施回执”推进。复用核心算法与证据治理规则，保留验证这些能力的有效测试；旧传输、schema、存储和绑定约束可以重新设计。完成项迁入 CHANGELOG/实施回执。

## 4. S0：固定基线，搭建服务骨架

**输入**：4.6.30 与已有技术方案。**产出**：可安装的服务验证切片与确定的运行合同。

步骤：

1. 盘点需要保留的代码解析、调用图、检索、影响分析和证据治理能力，定义 5.0 的工具/API/错误合同；旧版本分支仅用于源码追溯，不构成兼容验收目标。
2. 采用 FastAPI + Uvicorn 的 ASGI 服务和官方 Python MCP SDK，验证 Streamable HTTP 挂载、请求取消和生命周期，再锁定依赖版本。
3. 增加服务装配入口，区分服务配置目录和项目目录；启动不要求预先绑定 workspace。
4. 实现存活/就绪、端口冲突诊断、正常退出和无项目空态；就绪表示服务可接收请求，不伪装为所有项目索引都健康。
5. 验证前端空态的构建与 wheel 资源分发；同时确定本机启动、停止和自启动的安装策略。

预计模块：新增 `memory_center/service/` 装配、5.0 CLI 服务入口和打包资源；旧 HTTP bridge 与单空间 MCP 入口在相应切片移除或替换，不设置兼容转发。前端 Vue 3 + TypeScript + Vite 产物随 wheel 分发，用户运行时不需 Node.js。

验收：在没有 4.x 配置的环境安装构建产物后启动，能够打开空态管理页面；停止后端口与 worker 释放；只读取 5.0 配置，不自动发现或初始化旧数据。

停止条件：SDK 生命周期不清楚、wheel 缺静态资源、退出遗留进程。未解决前不进入多空间正式改造。

## 5. S1：建立服务控制面和多空间登记

**依赖**：S0。**产出**：空间目录应用用例、新项目识别预览、受控管理 API。

步骤：

1. 定义稳定 `workspace_id`、名称、源码根目录、服务划分、登记状态与配置版本；所有空间配置与数据统一受服务管理，不增加 external/managed 双模式。
2. 创建服务 `catalog.db`；登记/授权属于控制面，索引与任务仍归各空间事实库。
3. 实现识别预览、登记、列表、改名、暂停/恢复和移除接入；预览不初始化索引，不改写仓库说明或 Hook。
4. 从源码根目录重新识别项目与内部服务，空间配置、规则、索引和记忆全部写入独立的 5.0 数据目录；不读取已有 workspace.yaml。
5. 所有登记操作通过新目录应用用例进入 catalog；移除旧 registry 读写与导入路径，避免同名项目产生两套登记事实。

预计模块：`core/governance/registry.py`、`core/workspace/config.py`、`core/storage/workspace.py` 的边界梳理；新增目录存储/应用用例。修改每个具体符号前单独做 impact，不以本方案替代分析。

验收：登记两个独立源码项目；名称改变不改变 ID；路径不存在、软链接重复、重叠根目录都有明确结果；服务重启保留映射；源码目录中存在旧配置也不影响新空间登记。

失败恢复：未完成的登记事务不对外可见；已登记空间的首次索引失败可重试。5.0 运行数据采用本版本一致性备份恢复，不实现转换成 4.x 的兼容包。

## 6. S2：统一授权、请求上下文与 MCP 接入

**依赖**：S1。**产出**：多空间 MCP、共享授权规则、隔离回归与客户端连接合同。

步骤：

1. 实现端点配置：允许的空间、工具组、读写能力、速率/预算和可撤销凭据。首版可一个默认 `/mcp` 入口，多种凭据关联不同授权配置；不要求复制 WeKnora 的 URL 形式。
2. 将 HTTP/MCP 的授权规则收敛到共享应用边界；`tools/list` 隐藏未授权工具，`tools/call` 对直接调用再次拒绝。
3. 请求解析为不可变上下文，session 固定所属 workspace；显式空间与 session 冲突时拒绝。客户端 cwd/roots 仅帮助选择，不提供权限。
4. 为 5.0 工具重新定义空间路由与 schema，可复用现有任务级能力但不承担旧参数兼容；管理 API 不允许普通 AI 令牌登记路径或改授权。
5. 逐项核查 session/task/ref、缓存键、审计、取消和锁的作用域；同名符号、同名任务和相同 query 在不同空间必须独立。
6. 固化有界来源结果与错误合同；跨空间 group 查询保留每个空间的授权、新鲜度和证据边界。
7. 为原生 HTTP 客户端生成全新连接配置；如目标客户端确实需要 stdio，提供转发到 5.0 服务的薄代理，这属于客户端传输适配，不是旧单空间 MCP 模式。

预计模块：`mcp/server.py`、`mcp/runtime.py`、`mcp/tool_support.py`、HTTP 参数边界与相关用例；新增授权/目录解析层。旧实例的 `WorkspaceContext` 不能在并发调用中被原地切换。

验收：两个实际客户端使用 5.0 配置连接同一服务，同时在 A/B 项目查询、写入、恢复和关闭 session；交叉使用 ref/session、撤销令牌、直接调用隐藏工具均失败且无副作用；新 schema 有独立契约测试。

停止条件：出现一次空间污染、权限绕过或 session 错绑，即停止进入完整页面与发布阶段。

## 7. S3：整合后台任务与资源预算

**依赖**：S2。**产出**：统一任务管理投影、有界执行器与恢复流程。

步骤：

1. 核对 workspace jobs 与索引 coordinator 的不同任务记录路径，明确每类任务的权威账本；页面只读其投影，不自行修改状态。
2. 在现有任务准入上增加全局并发、每空间冲突与重任务预算；定义轻查询与索引执行的隔离方式。
3. 采用有界进程 Worker 隔离索引与请求处理，接受结构化、已授权的任务，不接受来自 MCP/页面的任意 shell；每个 Worker 自己打开 Store。
4. 接入阶段进度、取消确认、重复任务合并、重试 lineage 与发布失败诊断。
5. 实现关闭排空和重启租约核对；已失效任务标记 interrupted，不无限重试、不误报 completed。
6. 索引发布采用现有 staging/active generation 机制，失败继续读取上一 active generation。

预计模块：`application/jobs.py`、`core/workspace/jobs.py`、`core/indexing/job_coordinator.py` 与服务执行器。

验收：同请求合并、不同范围冲突有解释；多个空间共享资源有上限；查询在索引负载下保持有界；取消/崩溃/发布失败后账本准确，旧代际可读取。记录受控样本的延迟/内存基线，阈值由 S0/S3 实测确定，不在方案里虚构通过数值。

## 8. S4：实现独立管理页面

**依赖**：S1–S3 合同稳定。**产出**：用户可实际完成的项目管理流程。

页面按顺序实施：

1. 概览与项目列表：无项目、正常、stale、paused、失败等状态。
2. 添加项目向导：选择服务器可访问的源码目录 → 识别项目/服务 → 登记 → 显式首次索引。
3. 项目详情：服务组成、索引代际/覆盖、规则、受限工程记忆摘要。
4. 任务页面：进度、失败、取消、重试、冲突与排队预算。
5. MCP 接入页面：选空间/能力、创建凭据、复制连接配置、撤销/轮换。
6. 设置与维护：服务配置、模型状态、资源上限、一致性备份和恢复说明。

借鉴 WeKnora 的空间视图与后台任务可见性；布局围绕“添加项目并让助手使用”的流程设计。首版不增加完整聊天、Agent 浏览器、IM、沙箱或自动知识生成入口。

验收：仅通过页面完成两个项目的登记与索引、暂停/恢复和客户端配置；错误可恢复；页面刷新保持实际状态；浏览器不能访问未经授权的数据目录或管理密钥。

预计模块：新增 `frontend/` 与服务静态资源适配；页面调用统一管理 API。UI 端到端验证必须覆盖真实 API、空态、失败与重新启动，不能只使用 mock 页面作为交付证据。

## 9. S5：全新安装验收与 5.0.0 发布

**依赖**：S0–S4 验收通过。**产出**：安装包、全新安装/项目重建说明、发行回执与版本。

安装与验收流程：

1. 在空数据目录安装 5.0 候选版本，确认不依赖旧 workspace、registry、Hook 或宿主绑定。
2. 启动服务并通过管理页面登记两个源码项目，完成全量首次索引。
3. 生成全新 MCP 接入配置，为两个宿主明确授权并验证查询、工程记忆写入和隔离。
4. 核对新空间的服务/文件覆盖、active generation、任务和回执；失败项目显示可重试状态。
5. 验证重启、取消、令牌撤销与同版本备份恢复；安装包不包含旧入口兼容层。
6. 用户需要替换 4.x 时自行处理旧数据和宿主配置；5.0 不自动删除、导入或降级转换历史内容。
7. 通过版本与包资源检查后发布 5.0.0，更新 README、ARCHITECTURE、MCP_GUIDE、USER_GUIDE、REFERENCE 与 CHANGELOG。

版本策略：开发依赖和入口落地后再设 `5.0.0aN`，整链路稳定后设 `5.0.0rcN`，发布门禁通过才设 `5.0.0`。这些是预定阶段，不承诺日期；当前 pyproject 与已发布行为仍为 4.6.30。

发布阻断项：跨空间污染、不可解释的权限范围、首次索引/重试失败、索引失败覆盖 active generation、安装产物缺管理资源、5.0 工具契约或核心能力质量回归。

## 10. 后续 5.x 改造专题

| 专题 | 必须先解决的合同 | 可独立验收的最小交付 |
|---|---|---|
| 文档知识库 | 文档来源/版本/权限、解析幂等、更新删除传播、分块与引用、检索评测 | Markdown/文本摄取 → 增量索引 → 混合检索 → 引用原文；之后再加 PDF/Office 与连接器 |
